# Applications of OOP:
  In the rough prototype of the game, the principles of OOP that were used are Inheritance, Encapsulation, and Polymorphism. Inheritance was used in the game for mainly the items to be picked up or objects that can be interacted with. In this case it was the orange bubble that is spawned when you bubblized an enemy like in the actual game, and when you touch it, it pops and drops a spawner that spawns either a Cactus or Peach. It essentially spawns a fruit that also disappears when touched. If I had more time I would have implemented UI that tracks the score but otherwise, in both instances they inherit the base PickUp script to allow them to disappear when the player collides with it. As for Polymorphism, it was used also as those picks up dropped from enemies. They do carry over the protected OnTriggerEnter2D method, but it is set to be virtual. The main difference is that the pick ups are just set to disappear entirely when touched by the player, but for the orange enemy bubble it has extra behavior to where it can move side to side, and it calls on a manager script to drop the item spawner when touched before disappearing. Finally for Encapsulation for the enemy and player scripts, the speed of them can be modified in the inspector as public objects, along with other objects having public members for prefabs to be spawned in. However, certain members like moveX as an example for the player script (which is a float that gets the direction on the x axis where the player is moving) is kept private as no other script needs to access it.

# Singleton Pattern Application: 
  The Singleton design pattern was used in this for both a BubbleManager and SpawnerManager scripts. They were implemented with a base Singleton script (which was acquired from my other Unity projects from class assignments and activities to save time) where basically only one instance of the class can exist and persist in game, otherwise any other instances gets deleted. The two manager scripts then inherit from that base Singleton class, and become freely accessible scripts to be called upon in code without needing to directly reference them. The Bubble Manager's job is to instantiate an enemy bubble when the player uses the bubble projectile on the enemy. The enemy upon getting in contact with the bubble calls upon that script to use a method that takes the coordinates of the enemy and summons the bubble there. As for the Spawner Manager, when the bubble is popped by the player it calls a method that references the spawned in invisible item spawner prefab and calls upon its abstract method to spawn a fruit in place. The reason Singleton was implemented this way was to have enemies have access to global instances to do the work of instantiating bubbles and pick ups for them without needing references game objects for themselves, while making sure that these managers are the only things that exist to handle the work. 

# Factory Pattern Application: 
  The Factory design pattern was used for the ItemSpawner script for spawning in the fruit when the bubbles are popped. How it was done is the abstract Spawner script was first created, and the ItemSpawner script later derived from it. The SpawnerManager references it and calls on it's method to spawn the item. However, this script has references for two of the fruits prefabs and a private field for the selected fruit GameObject. Basically, when it gets called on it has a 50/50 chance of either spawning a Peach or Cactus to be collected. Whatever is chosen to be instantiated in place. This was implemented so that the SpawnerManager will create an item to be picked up by the player, but also make it where the spawner itself can be called on without a direct reference to it so the spawner doesn't need to know exactly what it is going to be spawning.
